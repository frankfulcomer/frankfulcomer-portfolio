Job Search Hub: Turning a Spreadsheet Problem into Software

A personal operational problem became an opportunity to build a maintainable application—and test it like a real product.

The problem

Tracking applications, companies, opportunities, and follow-ups across spreadsheets and job boards had become cumbersome. I wanted a more dependable system of record that could preserve history and eventually support better reporting and decision-making.

From learning exercise to useful product

After Workflow Tracker, I wanted to apply the same combination of QA judgment and AI-assisted development to something I would actually use. Job Search Hub is a Python/Flask application backed by SQLite, developed incrementally around documented requirements rather than a long wish list.

Designing for the work

The data model separates companies, applications, statuses, locations, and related information instead of treating everything as columns in one spreadsheet. That creates room for history, validation, and future integrations without requiring every future feature in the first release.

Quality is part of the product

The application and its Selenium/Pytest browser tests live in separate repositories. Requirements, architecture notes, and test strategy guide what is built and verified. Browser-level coverage is evolving alongside the application; the existence of a test repository does not imply every planned scenario is automated.

What this changed

Unlike the interview POC, this project has an ongoing practical purpose. It also creates a realistic setting for testing whether an AI-assisted development approach produces software that is useful, understandable, and maintainable—not just code that runs.

Where it leads

As the application and its testing grew, so did the need for a more consistent way to coordinate AI implementation, independent verification, and durable decisions. That work led toward the Conductor approach.

What the first release actually covers

Phase 1 deliberately begins after an application has been submitted. It records the employer and role, the original posting, where the job is located versus where the company is headquartered, employment and compensation details, and the application’s status history. The requirements also cover viewing, editing, searching, sorting, filtering, and archiving records. Recruiter management, job discovery, and AI-based job evaluation are intentionally future work, not features I am claiming to have shipped.

Why the database matters

A spreadsheet can show a current status, but preserving how an application moved through screening, interviews, and decisions requires a different model. I chose relational SQLite tables and explicit status-history records so the application can retain meaningful history rather than overwriting it. Even seemingly small distinctions—job location versus headquarters, compensation range versus basis, application date versus status-effective time—matter when the information is used later.

Testing a real workflow without touching real data

The separate Selenium/Pytest suite starts its own Flask application instance for each test, with a fresh disposable SQLite database. The tests use the browser like a user and, when persistence matters, inspect that same database read-only. This avoids corrupting actual job-search records and makes repeatable tests independent of whatever data happens to be in my working environment.

A concrete example of layered verification

Creating an application is more than clicking Save. A useful test checks the resulting screen and verifies that the database contains the right application and initial history record. Status-change scenarios also check that history is preserved in the right order. Other tests probe required fields and server-side validation. The suite is intentionally focused: duplicate handling, archive/restore, and exhaustive list filtering are among the documented future browser scenarios.

What I learned

The biggest shift was from demonstrating that I could automate a system to owning a system I actually wanted to improve. That made scope control, data integrity, test isolation, and maintainability practical concerns instead of portfolio talking points.
