Conductor: Making AI-Assisted Engineering Repeatable

A working method for combining human judgment, delegated AI implementation, independent verification, and a record of how decisions were made.

Why it exists

Using AI to accelerate one project is useful. Repeating that approach across projects exposed a different challenge: keeping intent, requirements, implementation, review, tests, and decisions aligned without turning every session into a copy-and-paste exercise.

The human stays responsible

I call the approach Conductor because I retain responsibility for the problem, priorities, tradeoffs, review, and acceptance. AI can help analyze, implement, debug, and test; it does not become the accountable engineer or decide what is good enough on its own.

Separating roles

The workflow distinguishes technical planning and independent review from delegated implementation. The current repository describes how Codex and Claude Code are coordinated, with explicit constraints on what delegated tools may change and separate authorization for commits and pushes.

Preserving evidence

A local bridge records scoped assignments, execution transcripts, changes, test evidence, reviews, and decisions. The aim is to make important work inspectable and repeatable while keeping raw transcripts and potentially sensitive context out of public repositories unless deliberately reviewed for publication.

Right-sized process

Conductor is not an attempt to impose ceremony on every task. The guiding rule is to use enough requirements, documentation, testing, and review to justify confidence—and stop when additional process no longer earns its cost.

Still evolving

This is an active engineering experiment, not a finished universal methodology. The portfolio itself is one place to apply it, learn where it creates friction, and refine the method.

From useful experiments to a repeatable method

Workflow Tracker demonstrated the speed of AI-assisted implementation. Job Search Hub made the stakes more practical: as a project grows, requirements, changes, test evidence, and decisions need to stay aligned. The next problem was how to coordinate that work without constant manual handoffs.

Who does what

I remain responsible for goals, scope, tradeoffs, and acceptance. The orchestration role prepares bounded assignments and independently reviews the resulting changes. Claude Code handles delegated implementation and debugging. Each role has a purpose, but the human retains authority over consequential decisions.

Facts, interpretation, authority

One of the workflow's central principles is that scripts establish facts, AI interprets facts, and humans grant authority. A test report is evidence, not permission to publish. An AI implementation summary is a starting point for review, not a substitute for inspecting changes and verifying behavior.

Making the process inspectable

A Python runner coordinates scoped tasks and records execution artifacts, source changes, test results, and review notes. Useful conclusions belong in project documentation; private transcripts preserve additional provenance where available. This separation keeps the public record readable without presenting reconstructed conversations as original evidence.

Guardrails without ceremony

Requirements are not silently rewritten to satisfy failing tests. Reviewing a change is separate from authorizing a commit or deployment. These boundaries matter, but so does keeping the workflow small enough that it saves effort rather than creating more of it.

What comes next

Conductor is still evolving through practical use. The question is not whether the process looks impressive on paper, but whether it makes development more reliable, efficient, and understandable across real projects.
